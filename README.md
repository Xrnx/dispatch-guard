# dispatch-guard

Keeps the orchestrator dispatcher replying to J first and checks each answer against J's rules.

Fallback (until a mid-turn prompt has been seen): on the main thread's 4th tool call in a turn it appends a reminder to the tool result telling the model to hand the remaining work to a background agent and reply to the user. Agent, SendMessage, TaskCreate and TaskUpdate calls do not count, nor do read-only calls (Read, Glob, Grep, ToolSearch, TaskGet, TaskList and any memory_read tool), and subagent calls are ignored. Finishing writes (Artifact publish, ArtifactData writes, memory_write/str_replace/append, propose_skills, SendUserMessage, SendUserFile) still count but never trigger the reminder (0.3.14); it fires once per turn, on the first non-finishing call at or past the 4th. It also flags foreground Bash calls that look long-running (node, python, npm test, playwright, sleep). It only warns: it never blocks or changes a tool call.

When J's prompt states a limit ("just f, i, j", "not just 40 keys", "except", "at most N", "both", "and also", "finish the limit"), it adds one `Scope:` line (at most 20 words) quoting the phrase, so the answer honours it (0.4.3). Plain "just"/"only" do not fire.

At the start of every chat (and again after /clear) it attaches one note to the first message telling the model to load the orchestrator skill before anything else, even for one-word or test messages. It fires once per chat.

running-proof: if a main-turn answer says "(running" with no launch id (agent, background Bash, trigger) from this turn and none still open from an earlier turn of the session, one correction line shows beneath the answer and reaches the model once with the next prompt.
parked-fix: if a main-turn answer names a fix ("should be a cheap fix", "needs to be fixed") but no launch id came back and no Edit, Write, NotebookEdit or Artifact ran this turn, one correction line shows beneath the answer; "(needs you)" and past-tense reports are exempt, at most once per turn, never blocks.
miss-landing (0.3.11): if a main-turn answer has a line opening `Miss:`, `Correction:` or `Gap:` (after optional bold or bullet) and nothing landed this turn (no Edit, Write, NotebookEdit, Artifact, propose_skills or memory_write/append/str_replace tool, no launch id), one line shows beneath the answer: fix it this turn or say which existing rule covers it. "no fix", "no rule change", "already covers", "existing rule" and "(needs you)" are exempt. It shares the once-per-turn slot with parked-fix and wins when both match; never blocks.
idle-guard: a Bash `rm` of the orchestrator ledger, or an answer saying "ledger cleared"/"queue empty", adds one reminder to read open-items and every backlog first; at most once per turn, never blocks.
board-timestamp: an ArtifactData set/update/batch whose `updated` is unparseable or more than 5 min from the live clock adds one line to that result ("re-stamp from `date`"); at most once per turn, main thread only, never blocks.

## Reply modes (0.6.16; 0.6.17 changes below)

Type `deep mode` or `light mode` (the whole prompt, optionally with please/now/on; a sentence that starts with it is not a command); the choice is stored and persists across turns. Default: deep.

- **Deep** (default): the assistant drafts the J-facing reply, calls the plugin tool `mcp__dispatch-guard__check_reply` with `{text, ask, evidence}` (`ask` = J's message verbatim, `evidence` = short summary of the tool results backing the claims), fixes every listed problem and rechecks until it returns `PASS <hash>`, then writes that exact text as its final reply (nothing before or after it). `check_reply` runs the deterministic checks (Correction/Prevention/Why lines, offers, parked fixes, unlanded misses, unsaved promises, missing **Leap:** / **Efficiency:** line on a substantive reply) and then the **AI judge**. A failure returns a numbered problem list as an ordinary tool result. Max 1 failure per draft in 0.6.17 (pack `deep-cap`; was 2), then PASS with a note; the count stays at the cap for the rest of that prompt (judge not called) and resets on a clean PASS or a new prompt. A `check_reply` from a subagent returns PASS without counts, logs or judge; an internal error returns `PASS (check error, fail-open)` and logs `error: "check_reply"`. Dark checks (`stop-figures`, `stop-sources`, `stop-writes`, `promise-proof`) are logged with `dark: true`, never failed.
  - **AI judge** (0.6.16, deep `check_reply` only): one `$.model.complete` call (`haiku`, effort low, 400 tokens, 8 s timeout, rules in a system block marked `cache: true`; the cache applies only above the model's minimum prompt size) judges the draft against the hook's own captured J message (the model's `ask` is only a fallback), the model's `evidence` summary, a hook-recorded slice (last 3000 chars) of this turn's tool results, and a generic rule set (a `</draft>` inside the draft is escaped) (claims backed by evidence, qualifiers kept, nothing left undone that the assistant could do, question answered first, correction names prevention and why the user caught it, no unbacked sweeping words, consistent dates and numbers, Efficiency line considers a sooner reply). It returns strict JSON `{"ok":bool,"problems":[...]}`; each problem fails the draft like a deterministic one and shares the 2-failure cap. **Fail-open**: an unanswered, timed-out, empty or unparseable reply leaves the deterministic result standing and logs `judge: "unavailable"` in `deepDenialLog`. When the judge answers, the narrow checks it covers generically (`open-question`, `unbacked-absolute`, `stop-dates`) are dark (logged, not failed); when it does not answer, and on the `SendUserMessage` fallback (which never calls the judge), they still fail. Light mode never calls it.
  - **0.6.17 faster deep mode**: (1) **Cap 1**: one failed check per draft, then PASS with a note; rule-pack value `deep-cap.numbers.cap` (0-3; 0 = never fail a draft). (2) **Short replies skip the judge**: under `deep-judge.numbers.minWords` words (default 60, pack 0-500) with no match of `deep-judge.patterns.claim` (Correction, Prevention, done/fixed/saved/verified/published/shipped/live/working/updated/changed/written/created) the judge is not called; the injected deep line also lets such replies skip `check_reply` and go out as the final text (turn-end checks still run; the final-text log row is `final: "short"`, not `"unchecked"`). (3) **Judge rules**: rewritten to flag only (a) contradicted claims, (b) unsupported done/verified/fixed/saved/working claims, (c) undone work the assistant could do, (d) an unanswered question; max 3 problems; never details merely absent from the evidence, paraphrases, or lines the user's standing rules require. Overridable by the pack: `deep-judge.messages.rules` (100-2500 chars). (4) **Evidence**: the hook keeps 1500 chars per tool result, 6000 total; the request stays about 4k tokens (ask 1500, evidence 2000, hook evidence 6000, draft 6000 chars). (5) `check_reply` loads the pack first, so pack values apply even when it is the session's first call. (6) **`set_rules`** (`mcp__dispatch-guard__set_rules`, `{text}`): the general mechanism for standing rules. Called once per session with the user's saved preferences, it stores up to 12000 chars (`standingRules:<session>`) and the judge gets them as a second cached system block ("flag clear breaches only; these rules can only add problems, never excuse one"). Absent: the judge runs as before. (7) **Efficiency-none check** (deterministic, cheap, counts toward the cap): after a failed round in the same prompt, "Efficiency: none" fails. Not implemented: the "tool calls before the first check not cited in the evidence" variant. (8) The deep line adds "Write the evidence first, then draft only claims it backs; label estimates, plans, requests, causes and a fix's intended effect as such (estimate / inferred / intended), never as fact." (9) offer-guard: "say so" followed by an opening bracket or quote (an instruction with examples) is no longer an offer.
  - **0.6.17 independent-check round**: `set_rules` is stored once per session (preference edits apply from the next session; later calls: "already set", except W22: a longer text replaces the stored one; subagents refused); its judge block says to use the rules for claims, undone work and whether a Leap/Efficiency line meets the user's own definition, never for a line's absence, order or format. Caps: judge problems tagged (a) contradicted or (b) unsupported claim get cap+1 (one extra judged round); all other problems keep `deep-cap`; the judge still runs at the cap and any (a)/(b) problems go into the PASS note and the Scoreboard row (`sent at cap`). Efficiency-none counts only when the effective cap is at least 2, else it goes into the note. The judge/skip claim pattern is widened (pass, complete, sent, uploaded, deleted, booked, tested, confirmed, ran, merged, pushed, deployed, yes ...) and a yes/no message from J never skips the judge. The deep line says "Fill the `evidence` field first". The local `deepDenialLog` also masks single-quoted spans.
  - **Review records (0.6.17)**: `deepDenialLog` failure rows now carry `problems` (sanitised: quoted spans become `"[…]"`, 160 chars each; deterministic checks keep only their generic lead, never draft words). Each failed draft with an outcome queues a Scoreboard `corrections` row through the existing `corrLog` flush: `source: "deep"`, `category: "pre-send"`, `date` (SGT `YYYY-MM-DD`), `time` (SGT `HH:MM`), `session`, `check_ids[]`, `problems[]` (generic labels only: unsupported claim, contradicted claim, undone work, unanswered question, footer/format, other; the judge prefixes each problem with its rule letter (a)-(d) and the label comes from that, deterministic checks map by id; problem text never reaches the Scoreboard), `outcome` `"fixed"` (a clean PASS followed in the same prompt) or `"sent at cap"` (passed through the cap); `words` is empty (no reply text). A failed draft whose prompt ends with no later check has no row. `judgeLog` rows add `input`, `output`, `cache` tokens (from the call's `usage`), and `judgeTokens` keeps today's SGT total `{date, calls, input, output, cache}`.
  - **0.6.18 session evidence**: per session (main thread only) the hook keeps a rolling store `sessionEvidence:<session>` (last 24000 chars, oldest dropped) of every tool result (tool + first 800 chars), every agent hand-back / `SubagentHandback` / agent-message / task-notification delivered to the main thread (first 1500 chars; also indexed with timestamps in `agentReports:<session>`) and the assistant's final reply per turn (first 600 chars). The judge prompt gets the last 12000 chars of it, most recent first, as `<session_evidence>` after `<hook_evidence>`; the whole request is held to about 6k tokens (24000 chars) and the session block is trimmed first. JUDGE_RULES say a claim backed there is backed. Rule-pack `deep-evidence.numbers`: `sessionChars` (0-40000, default 24000; 0 = off) and `judgeChars` (0-20000, default 12000). Evidence is recorded in deep mode only. The assistant's own prior replies are kept for the Session facts line but never shown to the judge, and the running turn's tool results are left out of the block (they are already in hook_evidence). Retention: local store only, a `sessionIndex` keeps the last 20 sessions and clears the evidence and agent reports of older ones. Unsanitised, never written to the Scoreboard. **Session facts line** (writer side): on each J prompt in deep mode (main thread only, never light mode or agent prompts) one context line `Session facts: agents running: N; last agent reports: <time · 80-char head> x3; last reply: <80-char head>; versions seen in tool results: ...` is injected, bounded by `deep-evidence.numbers.factsChars` (0-2000, default 700; 0 = off).
  - **0.6.19 deep-stats**: at each deep-mode J-prompt turn end the hook upserts ONE Scoreboard `corrections` row per session per day, doc id `deepstats-<session>-<date>` (op `set`, same queue/flush as other rows, so it flushes only where the permission check already allows), `{source: "deep-stats", date (SGT), session, plugin_version, prompts_judged, first_draft_pass, unchecked, rounds_total, judge_calls, judge_ok, judge_unavailable, tokens_in, tokens_out, tokens_cache}`. `prompts_judged` = deep J prompts whose reply went through check_reply (or the SendUserMessage fallback check) plus short replies that skip it; `first_draft_pass` = of those, prompts with no failed round (a short direct reply counts as a pass; a long final text with no check is not counted in either, and goes into `unchecked` instead; a prompt answered only via SendUserMessage is counted at turn end from its check rounds). `rounds_total` = check rounds (epoch state in `deepStats:<session>`, written beside deepOpen/deepDenials). Judge and token figures are running per-session, per-SGT-day totals kept in `deepStats:<session>`, incremented at each judge call (`judge_ok` = answered, ok or fail; `judge_unavailable` = no usable answer). The flush removes a queued entry only if its data is unchanged since it was sent. Counts only: no draft, problem or evidence text. Light mode writes nothing.

## How updates ship

Two routes; pick by what changes.

| Change | Route | J uploads? |
|---|---|---|
| A trigger regex, threshold or message text of an existing check; a new pattern-only check | **Rule pack** (data) | No |
| Anything else: new logic, new hook, a check that needs state or counting | **Code** release | Yes (one zip) |

### Rule pack (no upload)

At the first hook call of a session the hook fetches `https://raw.githubusercontent.com/Xrnx/dispatch-guard/rulepack/rulepack.json` (branch `rulepack`, 3 s cap, cached for the session). The hooks runtime forbids `eval`/`new Function`/`import()`, so only data is fetched, never code.

- **Valid and newer** (`version` > bundled, currently 4) → overrides merged per check id onto the bundled rules (hooks/rulepack.ts `BUNDLED`).
- **404 / `{"disabled": true}` (kill switch) / version ≤ bundled** → bundled rules, silently.
- **Timeout, HTTP error, bad JSON, schema miss** → bundled rules plus one context note per session (`rulepack: … — using bundled v4`).
- The upload-check line ("uploaded") ends `rulepack vN (fetched|bundled)`.

Schema:

```json
{
  "version": 2,
  "disabled": false,
  "checks": {
    "<known check id>": {
      "patterns": { "<key>": "case-insensitive source" , "<key2>": { "source": "...", "flags": "im" } },
      "numbers":  { "<key>": 30 },
      "messages": { "<key>": "≤200 chars; only the {placeholders} the bundled text has" }
    }
  },
  "add": [ { "id": "new-id", "on": "answer|prompt|tool", "pattern": "regex", "message": "≤200 chars" } ]
}
```

Validation (same code at runtime and in the publish tool): known check ids and keys only; every regex compiles (flags `i m s u` only); numbers inside each key's range (`RANGES` in hooks/rulepack.ts); messages non-empty, ≤200 chars, no new placeholders; ≤20 added checks with fresh ids. Added checks: `answer` → one line under the answer, `prompt` → context on J's prompt, `tool` → note on a main-thread tool result (matched against tool name + input JSON). Never a block.

Publish: `tools/rulepack-publish.sh --init pack.json` (writes the bundled rules as v2 to edit), then `tools/rulepack-publish.sh pack.json` validates and prints the git commands that push it to branch `rulepack` (it runs none of them). New sessions pick it up; raw.githubusercontent may cache up to ~5 min.

### Code release (upload)

Every version bump adds its CHANGELOG.md line in the same commit.

Bump `.claude-plugin/plugin.json`, run `claude plugin test .` and `claude plugin validate .`, zip, J uploads. Bump `BUNDLED_VERSION` when the bundled rules change, so an older published pack stops overriding them. Once org sync is set up (claude.ai Organization settings > Plugins & skills > Sync from GitHub, private repo, default branch `stable`), `tools/promote.sh <release-remote> stable` replaces the upload: it refuses a dirty tree and pushes only when the suite passes.
